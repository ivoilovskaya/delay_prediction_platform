# ML-модуль

Рабочий цикл: `ml.worker` читает из общей базы `telemetry` и `schedule_plan`, через `ml.db.run_cycle` строит признаки и вызывает `ml.predictor.DelayPredictor`, затем записывает историю прогнозов в таблицу `predictions`. Один цикл охватывает несколько транспортных средств. Модель загружается при запуске worker; при её недоступности используется baseline.

Замеры `read`, `predict`, `write`, `total` (мс) входят в журнал worker; `DelayPredictor.last_timing` содержит замеры построения признаков и инференса. Расчётные признаки в рабочем цикле не сохраняются. Отдельные файлы `artifacts/features/*.csv` относятся к обучению и создаются `ml.dataset`.

Для ручной проверки модели есть отдельное приложение `ml.service` с HTTP-методами `POST /predict`, `POST /predict/batch` и `POST /predict/from-db`. Последний метод по умолчанию добавляет прогнозы в БД. Формат и метрики обучения описаны в [README_ML.md](../README_ML.md).

### Производительность воркера

Каждая попытка обработки пишет строку `ML_CYCLE {JSON}` в лог. БД для этих
метрик не используется. Сводка по последним 100 попыткам (включая ошибки):

```bash
docker compose logs --no-color --no-log-prefix worker | python -m scripts.worker_stats --last 100
```

При запуске без Docker сохраните stdout и stderr воркера в файл, затем:

```bash
python -m scripts.worker_stats worker.log --last 100
```

Команда использует только стандартную библиотеку Python. Если записей меньше,
показывает доступное количество (`cycles`); `null` означает отсутствие замеров.
Периоды ожидания новых данных не считаются циклами.

- `vehicles_per_cycle_avg/max`: размер обработанного батча. Признаки считаются
  последовательно, инференс выполняется батчами по режимам; это не число потоков.
- `cycle_ms_avg/max`: время от начала попытки (включая получение T) до сохранения
  прогнозов; без сна между циклами. Учитываются и неудачные попытки.
- `cycles_over_interval`: сколько попыток заняли больше интервала запуска.
- `predict_ms_per_vehicle`: суммарное время этапа прогнозирования / количество
  автобусов. Это удельные затраты батча, а не индивидуальная latency ответа.
- `features_ms_per_vehicle`, `inference_ms_per_vehicle`: взвешенные затраты на
  автобус только по циклам с замерами модели (`model_timed_cycles`). Инференс —
  вызовы `predict_frame`, без подготовки DataFrame/последовательностей и записи БД.
- `failed_cycles`: ошибки цикла; `baseline_predictions`: прогнозы baseline
  (включая явный выбор baseline, отсутствие модели и сбои признаков/модели);
  `skipped_vehicles`: автобусы без подходящих данных/цели.

Длительность цикла помогает оценить задержку выдачи прогноза, но сама по себе
не гарантирует свежесть: исходная телеметрия тоже может поступить с опозданием.
В Docker для worker включена ротация: 3 файла по 10 МБ. Логи сохраняются при
перезапуске контейнера, но удаляются при его удалении/пересоздании; история не
является долговременным архивом. Новая настройка применяется при пересоздании
worker. Для локального файла ротацию настраивает разработчик.

### Измерения в historical-режиме

Сервис `replay` пишет `REPLAY_CYCLE {JSON}` после каждой попытки шага.
Применить изменения к уже запущенному historical-проекту:

```bash
docker compose -f compose.historical.yaml up -d --build --no-deps replay
```

После накопления циклов получить сводку (Python 3 на хосте, без ML-зависимостей):

```bash
docker compose -f compose.historical.yaml logs --no-color --no-log-prefix replay | python3 -m scripts.worker_stats --last 100
```

Или выполнить команду сводки внутри работающего контейнера:

```bash
docker compose -f compose.historical.yaml logs --no-color --no-log-prefix replay | docker compose -f compose.historical.yaml exec -T replay python -m scripts.worker_stats --last 100
```

`cycle_ms_avg/max` теперь относятся ко всему шагу replay: подготовка,
ML, аналитика и публикация нового времени для API. `ml_ms_avg` включает чтение
БД, прогнозирование и запись прогнозов; `analytics_ms_avg` — расчёт аналитики.
Средние этапов и показатели автобусов учитывают только успешные шаги;
ошибки входят в `failed_cycles` и длительность цикла. Загрузка модели,
создание сессии и пауза между шагами в замер не входят.

`cycles_over_step` сравнивает время обработки с `REPLAY_STEP_S` (по умолчанию
10 секунд времени потока). Это ориентир способности обрабатывать поток в
реальном времени. `REPLAY_TICK_S` — дополнительная пауза после каждого шага,
а не срок выполнения: реальный период равен длительности шага плюс пауза.
Счётчик не гарантирует свежесть исходных данных.

Сводка берёт последние N попыток из доступных логов, в том числе из разных
сессий replay. Полные записи содержат `session` и `T`. Если история дошла до
конца, новые циклы не появляются: запустите воспроизведение заново через
интерфейс. При пересоздании контейнера его старые логи удаляются.
