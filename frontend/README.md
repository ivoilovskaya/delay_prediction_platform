# Диспетчерский экран

Интерфейс расположен в `frontend/dispatcher/` и открывается через FastAPI на `http://127.0.0.1:8000/`. Папка `Frontend Test` — отдельный черновой макет.

Запуск с эмулятором и демонстрационным расписанием:

```bash
bash scripts/setup_and_run.sh --mode emulator --demo-plan
```

Для исторических данных: `bash scripts/setup_and_run.sh --mode historical`. Исторический режим показывает состояние на время последней телеметрии, а не текущее движение. Маршруты и аналитику участков нужно подготовить отдельно по [инструкции](../analytics/README.md).

Экран раз в 15 секунд читает готовые данные из FastAPI:

| Запрос | Что даёт экрану |
|---|---|
| `GET /vehicles/active` | Координаты активных ТС и уже сохранённые прогнозы задержки |
| `GET /analytics/segments` | Маршруты, участки, время прохождения и уровень риска |
| `GET /analytics/vehicles` | Проверенную привязку ТС к маршруту и участку |

На карте линии между остановками **схематичны**; это не дорожные траектории. ТС с актуальной GPS-точкой показаны кругами. Серый участок означает недостаток данных, зелёный — норму, жёлтый — внимание, красный — высокий риск. Для выбранного инцидента показаны участок, обычное и текущее время прохождения, привязанные ТС и свежий прогноз опоздания, если он есть. Вероятность и внешняя причина (авария, поломка, пробка) по этим данным не определяются. Фактор «замедление по GPS» показывается только при подтверждении несколькими ТС. Прогноз остановки не приписывается участку без явной связи.

Публичная картографическая подложка и библиотеки Leaflet/MapLibre загружаются из сети. Если сеть недоступна, список инцидентов и карточка остаются доступны. Для автономной установки эти ресурсы нужно разместить локально. Браузер не обращается к БД и не запускает расчёт; их выполняют сервер и воркеры.

Проверки:

```bash
python -m pytest -q
node --check frontend/dispatcher/assets/app.js
node --test tests/dispatcher-data.test.cjs tests/dispatcher-ui.test.cjs
```
