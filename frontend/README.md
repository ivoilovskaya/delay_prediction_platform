# Фронтенд: работа с FastAPI и данными транспорта

Это инструкция для разработчика диспетчерской. Рабочий интерфейс находится в `frontend/dispatcher/` и открывается на главной странице FastAPI. Старый табличный `frontend/index.html` удалён. Папка `Frontend Test` — самостоятельный исходный макет; приложение её не обслуживает.

## Запуск

Из корня репозитория, в уже настроенном окружении Python 3.12:

```bash
bash scripts/setup_and_run.sh --mode emulator --demo-plan
```

Открыть http://127.0.0.1:8000/. Если порт занят, добавить `--port 8002`. Для этого сценария нужны работающий Docker и локальный образ/архив эмулятора. Скрипт не устанавливает пакеты без явного `--install`. Подробности первоначальной установки — в [корневом README](../README.md).

`--demo-plan` использует настоящий TCP-поток эмулятора, общую БД и ML, но **искусственное расписание и случайное движение**. Это проверка интеграции, не качества прогнозов на реальных маршрутах.

Без Docker можно использовать исторические CSV:

```bash
bash scripts/setup_and_run.sh --mode historical
```

Для работы только над страницей можно запустить backend без приёмника и ML:

```bash
.venv/bin/python -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

Без `DATABASE_URL` карта будет пустой — это штатное состояние. Чтобы читать существующую базу, задайте `DATABASE_URL` и `ML_TIME_MODE=wall` для живого потока либо `stream` для исторических данных. Сам backend базу не заполняет и прогнозы не рассчитывает. `.env` автоматически не загружается.

Страница и API работают на одном origin, поэтому запросы имеют относительные адреса. Если используете отдельный dev-сервер фронтенда, настройте proxy на FastAPI либо согласуйте CORS для конкретного origin. Сейчас CORS middleware не настроен. Открытие HTML как `file://` не подходит для работы с API.

## Как данные доходят до интерфейса

```text
Эмулятор → TCP-приёмник → telemetry в общей БД
Актуальный план → schedule_plan в той же БД
ML-воркер → читает телеметрию и план → пишет predictions
Браузер → GET /vehicles/active → FastAPI читает БД → JSON → карта и карточки
```

Браузер не подключается к SQLite/PostgreSQL напрямую и не получает реквизиты БД. Запрос страницы не запускает ML: он читает уже сохранённый результат. В сценарии эмулятора воркер работает каждые 10 секунд по умолчанию; частота настраивается через `ML_INTERVAL_S`.

Текущая задержка — отдельная оценка сопоставления GPS и плана, которую вычисляет backend при подготовке обзора. Её нельзя подменять прогнозом будущей задержки.

## Доступные запросы

Swagger: http://127.0.0.1:8000/docs. Машинная схема: `/openapi.json`. Сейчас ответы описаны обычными словарями, поэтому точный состав полей дополнительно сверяйте с этой инструкцией и кодом.

| Метод и путь | Назначение | Ответы |
|---|---|---|
| `GET /vehicles/active` | Основной запрос карты: ТС, GPS, остановки, текущая задержка и сохранённый прогноз | 200; 503 при ошибке БД |
| `GET /predictions/latest` | Последний сохранённый прогноз каждого ТС, включая ТС без свежей телеметрии | 200; 503 |
| `GET /predictions/{tr_id}/latest` | Последний сохранённый прогноз одного ТС | 200; 404, если прогноза нет; 503 |
| `GET /health` | Жив ли HTTP-процесс | `{"status":"ok"}`; не проверяет модель и БД |

У этих методов пока нет query-параметров для фильтрации, сортировки или пагинации. Текущие поиск, геофильтры и пороги выполняются на клиенте. Некорректный тип `tr_id` возвращает 422. Ошибка API имеет вид `{"detail":"…"}`.

`/dispatcher` и `/dispatcher/` перенаправляют на `/`. Ресурсы доступны по `/dispatcher/assets/…`. Старый `/dispatcher/replay` удалён: карта больше не загружает статическую запись.

Отдельный сервис `ml.service` с `/predict` и `/predict/batch` не нужен для обычной работы экрана и общим скриптом не запускается. Интерфейс читает готовые прогнозы через backend.

## Основной ответ: GET /vehicles/active

Сокращённый пример структуры (значения условные):

```json
{
  "mode": "live",
  "demo_plan": false,
  "reference_time": "2026-09-27T10:00:00+00:00",
  "active_window_s": 120,
  "vehicles": [
    {
      "tr_id": 42,
      "unit_id": 1166336,
      "event_time": "2026-09-27T09:59:58+00:00",
      "telemetry_age_s": 2,
      "position": [55.75, 37.5],
      "speed_kmh": 20,
      "current_delay_s": 30,
      "delay_source": "gps_plan_estimate",
      "status": "on_route",
      "has_schedule": true,
      "track": [[[55.749, 37.499], [55.75, 37.5]]],
      "current_stop": null,
      "next_stop": {
        "id": 100,
        "name": "Адрес остановки",
        "position": [55.751, 37.501],
        "planned_time": "2026-09-27T10:02:00+00:00"
      },
      "stops": [],
      "prediction": {
        "tr_id": 42,
        "t_forecast": "2026-09-27T10:00:00+00:00",
        "predicted_at": "2026-09-27T10:00:01+00:00",
        "target_stop_id": 200,
        "target_stop_name": "Адрес целевой остановки",
        "target_position": [55.76, 37.51],
        "target_time_plan": "2026-09-27T10:12:00+00:00",
        "predicted_delay_s": 87,
        "predicted_arrival": "2026-09-27T10:13:27+00:00",
        "interval_lo_s": 60,
        "interval_hi_s": 120,
        "model_used": "ensemble",
        "fallback_reason": null,
        "degraded": false,
        "status": "ready"
      }
    }
  ]
}
```

Ответ может содержать дополнительные поля, например внутренний `id` записи прогноза. Не полагайтесь на порядок полей.

### Общие поля

- `mode`: `live` — относительно текущего времени; `historical` — относительно последней точки телеметрии в БД. Исторический режим не означает интерактивное проигрывание архива.
- `demo_plan`: признак искусственного демонстрационного расписания. Показывайте явную пометку.
- `reference_time`: момент состояния, ISO UTC, либо `null`, если момент не определён.
- `active_window_s`: сейчас 120 секунд. В список попадает ТС с достоверной доступной точкой не старше этого окна относительно `reference_time`.
- `vehicles: []`: нормальный пустой ответ, а не ошибка. База может ещё не быть настроена или телеметрия не поступает.

### Поля транспорта и география

| Поле | Значение |
|---|---|
| `tr_id` | ID транспорта, **не номер маршрута** |
| `unit_id` | ID бортового устройства, может быть `null` |
| `event_time`, `telemetry_age_s` | Время последней достоверной точки и её возраст относительно момента состояния |
| `position` | `[широта, долгота]`, подходит для Leaflet; это **не** порядок GeoJSON `[долгота, широта] |
| `speed_kmh` | Скорость в км/ч, может быть `null` |
| `current_delay_s` | Текущая оценка задержки в секундах; `null`, если данных недостаточно |
| `delay_source` | `gps_plan_estimate` для оценки по GPS/плану, иначе `null` |
| `status` | `on_route`, `no_plan`, `outside_schedule`, `off_route` |
| `has_schedule` | Найден ли план для ТС в рассматриваемом окне |
| `track` | Массив сегментов GPS за последние 10 минут; каждый сегмент — массив `[широта, долгота]` |
| `current_stop` | Ближайшая точка плана в радиусе 60 м либо `null`; это не подтверждение прибытия |
| `next_stop` | Следующая точка по плану с учётом доступной оценки задержки либо `null` |
| `stops` | До 100 плановых точек на следующие 25 минут |
| `prediction` | Последний сохранённый прогноз либо `null` |

`on_route` означает соответствие доступному временному окну плана, а не подтверждённый диспетчером выпуск на маршрут. `off_route` — большое расстояние при сопоставлении трека и плана, не установленная причина отклонения.

GPS-сегменты разделяются при невалидной точке или паузе больше 90 секунд. Не соединяйте разные сегменты линией. Число точек ограничивается для отображения, поэтому это не API выгрузки сырой телеметрии.

Объекты остановок имеют поля `id`, `name`, `position`, `planned_time`. `name` может быть `null`: тогда показывайте ID. ID соответствует событию расписания `tt_action_item_id`, а не гарантированно постоянному ID физической остановки. Линии между плановыми точками — схема, а не геометрия дорог.

### Прогноз

- `t_forecast`: момент состояния, для которого выполнен расчёт.
- `predicted_at`: время выполнения расчёта.
- `target_stop_id`, `target_time_plan`: целевая плановая остановка и время. При расчёте она выбирается в окне `(T+10 минут, T+15 минут]`.
- `predicted_delay_s`: прогноз задержки **в секундах**, не текущая задержка.
- `predicted_arrival`: рассчитанное время прибытия; уже содержит задержку, прибавлять её повторно не нужно.
- `interval_lo_s`, `interval_hi_s`: границы интервала задержки в секундах, могут отсутствовать как значения (`null`). Это не вероятность пробки.
- `model_used`: например `ensemble`, `boosting`, `catboost`, `torch`, `baseline`.
- `fallback_reason`: причина резервного расчёта, если есть.
- `degraded`: признак неполной телеметрии/деградации расчёта. Показывайте отдельно от свежести.
- `status`: `ready` или `stale`. По умолчанию прогноз устаревает через 90 секунд по более старому из `t_forecast` и `predicted_at`, относительно часов сервера; в режиме replay — относительно текущего времени воспроизведения.

`target_stop_name` и `target_position` обогащаются планом именно в `/vehicles/active`; могут отсутствовать либо быть `null`. В отдельных `/predictions/…` этих полей нет. Если координат цели нет, сохраняйте численный прогноз в карточке, не рисуйте вымышленную точку на карте.

Положительная задержка — опоздание, отрицательная — опережение. `null` нельзя превращать в ноль: это отсутствие оценки. Все временные строки трактуются как UTC; клиент показывает их через `Intl.DateTimeFormat` с `timeZone: 'Europe/Moscow'`.

## Отдельные запросы прогнозов

`GET /predictions/latest` возвращает:

```json
{"status": "unavailable", "predictions": []}
```

При наличии записей `predictions` содержит последние прогнозы по ТС. Общий статус — `ready`, если хотя бы один свежий, иначе `stale`. Проверяйте **статус каждой записи**, а не только общий. Этот список не заменяет список активного транспорта: в нём могут быть ТС без свежей телеметрии.

`GET /predictions/42/latest` возвращает непосредственно объект прогноза, без обёртки `predictions`. При отсутствии записи — 404. Ошибки БД возвращаются как 503; `/health` при этом может оставаться успешным.

## Как устроен текущий клиент

- [dispatcher/index.html](dispatcher/index.html) — разметка.
- [dispatcher/assets/style.css](dispatcher/assets/style.css) — оформление.
- [dispatcher/assets/data.js](dispatcher/assets/data.js) — адаптер JSON API в модель карты, формат времени, классификация сигналов.
- [dispatcher/assets/app.js](dispatcher/assets/app.js) — запросы, карта, карточки, поиск и обработчики интерфейса.

`refresh()` в `app.js` отправляет `GET /vehicles/active`, затем `DispatcherData.adapt()` преобразует ответ. Например, `tr_id → id`, `current_delay_s → currentDelay`, `prediction → forecast`. Значения прогнозов берутся из ответа без генерации на клиенте.

Сейчас запрос имеет `cache: 'no-store'` и `AbortSignal.timeout(10000)`. Флаг `loading` запрещает параллельные обновления. Следующий запрос планируется через 5 секунд после завершения предыдущего. При сбое прежние координаты остаются с пометкой потери связи, маркеры тускнеют, прогнозы скрываются и актуальные сигналы не выдаются. При успешном пустом ответе прежний транспорт убирается с карты.

Пример одиночного запроса для собственного компонента:

```js
const response = await fetch('/vehicles/active', {
  cache: 'no-store',
  signal: AbortSignal.timeout(10000),
});
if (!response.ok) throw new Error(`HTTP ${response.status}`);
const snapshot = await response.json();
// snapshot.vehicles → ваша модель представления → карта/карточки
```

### Свежесть и карточки

Показывается только прогноз со статусом `ready`, при актуальной телеметрии
(не старше 120 секунд) и доступном API. Устаревший прогноз полностью исключается
из карточек, счётчиков, подсказок карты и окраски участков. Сам автобус остаётся,
если его координаты актуальны. При восстановлении связи используются новые данные API.

Источник прогноза, название модели и техническая причина резервного расчёта
в интерфейсе не показываются. Поля `model_used` и `fallback_reason` остаются
в API для разработчика. Пометка неполной телеметрии сохраняется.
Карточка инцидента содержит ТС, участок, задержку и текст «причина не установлена»:
причину опоздания и вероятность сбоя текущие данные не определяют.

### Цвета участков

Порог выбирается в интерфейсе: 2, 5 или 10 минут (по умолчанию 5).

- **Красный** — текущая оценка задержки достигла порога. Выделяется отрезок
  от положения автобуса к следующей остановке, а не участок у будущей цели прогноза.
- **Жёлтый** — свежий прогноз достиг порога; выделяется участок перед целевой остановкой.
- **Зелёный** — для участка есть актуальная оценка ниже порога.
- **Серый** — данных для оценки недостаточно. Отсутствие прогноза не означает норму.

Текущий красный и будущий жёлтый участки могут отображаться одновременно.
На совпадающем направленном отрезке красный имеет приоритет над жёлтым,
жёлтый — над зелёным. Маркер автобуса также отдаёт приоритет текущей задержке.
Текущая задержка является оценкой сопоставления GPS и расписания, а не
зарегистрированным фактом прибытия.

Карта показывает схемы движения всех автобусов в выбранной зоне; переключатель
остановок управляет этим слоем. Линии между остановками схематичны, без привязки
к дорожной сети. История GPS выделена нейтральным цветом, последний GPS-отрезок
окрашивается только по текущей оценке задержки. Аналитика замедления остаётся
отдельным разделом: её статусы не подменяют прогноз задержки, а геометрия маршрутов
отображается нейтральным слоем.


## Можно ли придумать другие запросы? Да

**Фронтендер может по своему усмотрению предложить другие методы API, параметры и структуру ответов под интерфейс. Текущий набор запросов не является обязательным окончательным решением.** Можно менять композицию экрана, адаптер, фильтры и способ получения данных.

Например, могут понадобиться `GET /vehicles/{tr_id}`, отдельный запрос трека за период, фильтрация по зоне на сервере, пагинация или общий `/dashboard`. **Это примеры предложений, сейчас таких методов нет.** Один лишь новый URL в `fetch()` не создаёт endpoint: его нужно реализовать в FastAPI.

Для каждого предложения опишите:

1. Какому экрану и действию оно нужно, HTTP-метод и URL.
2. Входные параметры и пример JSON-ответа, единицы и формат времени.
3. Какие поля допускают `null`, как выглядят пустой ответ и ошибки.
4. Частоту обновления и ожидаемый объём данных.
5. Источник каждого нового поля. Номера маршрутов, автопарки, резервы и причины задержек пока не доступны автоматически.

Далее согласуем контракт и реализуем нужный backend. Изменения маршрутов — в `backend/endpoints.py`, чтение/подготовка данных — в `backend/vehicles.py` и `backend/predictions.py`. Прямого доступа браузера к БД и запуска ML на каждое обновление экрана не добавляем. Если меняется существующий контракт, одновременно обновляем клиент, документацию и тесты.

## Проверки перед передачей изменений

```bash
.venv/bin/python -m pytest -q
node --check frontend/dispatcher/assets/app.js
node --test tests/dispatcher-data.test.cjs tests/dispatcher-ui.test.cjs
```

Для JS-тестов нужен Node.js 22+, установка npm-пакетов не требуется. Проверки клиента охватывают адаптацию данных, скрытие устаревших прогнозов и потерю связи, правила окраски текущего и будущего участков, карточки и слои карты с имитацией DOM/Leaflet. Это не визуальное тестирование браузером.

В браузере проверьте: пустую базу, ТС без плана/прогноза, устаревший прогноз, baseline, потерю и восстановление связи, пустую геозону, смену выбранного ТС, подписи остановок и отсутствие интернета для карты. Список и карточки должны оставаться работоспособными при недоступной подложке.
