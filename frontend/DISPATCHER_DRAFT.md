# Черновик интерфейса диспетчера

Откройте `frontend/dispatcher-draft.html` в браузере. Это автономный макет с вымышленными данными, без сетевых запросов. Он не подключён к FastAPI и не заменяет текущий `frontend/index.html`.

## Задача экрана

Помочь диспетчеру быстро понять, у какой остановки и у какого автобуса ожидается задержка, когда это произойдёт и какова оценка задержки. Решения диспетчера и инструкции по действиям в этот черновик не входят.

Слева — список прогнозов, справа — подробности выбранного прогноза. Нажатие на карточку меняет подробности. Крупные подписи, цвет продублирован текстом, управление доступно с клавиатуры. На узком экране подробности располагаются под списком.

Все маршруты, названия остановок, транспорт, времена и оценки в макете вымышлены. Время не обновляется: 12:00 — момент демонстрационного сценария. Порядок карточек задан вручную. Красный статус «Задержка от 5 минут» — иллюстрация величины задержки, не оценка вероятности и не утверждённый порог риска.

## Состояния

В коде `options.scenario` поддерживает `ready`, `empty`, `stale`, `offline`. При наличии прогноза показываются карточки; в остальных состояниях прогнозы скрываются и выводится явное сообщение. Пустой ответ или потеря связи не означают отсутствие задержек. `options.size` поддерживает `normal` и `large`. Встроенный просмотр в Codex предоставляет переключатели этих вариантов при поддержке Tweak; для автономного файла значения можно менять в коде.

## Подключение к FastAPI: что согласовать

Текущий `/predictions/latest` в `main` отдаёт демонстрационные `state` и `delay`; данных для этого экрана недостаточно. В `feature/ml` есть прогноз для отдельного ТС с `tr_id`, `target_stop_id`, `target_time_plan`, `predicted_delay_s`, `predicted_arrival`, `interval_s`, `predicted_at` и `degraded`. Это ещё не готовый список для диспетчера.

Предлагаемый контракт, который нужно согласовать до реализации:

- Список актуальных прогнозов по автобусам, стабильный ID каждого элемента.
- ID/номер маршрута, направление, ID автобуса, ID/название целевой остановки. Читаемые названия должны поступать из справочника, их нельзя выдумывать по ID модели.
- Время прогноза, время последней телеметрии и срок актуальности (ISO 8601 с часовым поясом).
- Плановое время прибытия, ожидаемое время прибытия, задержка в секундах; интервал задержки — необязательный.
- Признак устаревших или неполных данных, причина отсутствия прогноза при наличии такой информации.
- Вероятность конкретного события — только если бэкенд рассчитывает её отдельно и указывает событие/порог. Интервал прогноза и ROC-AUC нельзя показывать как вероятность опоздания.

На фронтенде: периодически получать готовый список через GET с согласованным интервалом, не допускать перекрывающихся запросов, отменять запросы по таймауту, проверять формат и свежесть данных. Нельзя запускать вычисление модели каждым обновлением экрана. Отображать прошедшие целевые времена и свежесть с учётом времени сервера.

Порог значимой задержки, сортировку и правила уведомлений согласовать с командой. Прогноз по участку требует привязки к географии и отдельного правила объединения прогнозов нескольких автобусов. До этого интерфейс показывает прогноз у остановки для конкретного автобуса.

## Проверка

Синтаксис JavaScript проверен. Просмотр локального файла инструментом браузера заблокирован политикой доступа к URL; визуальная проверка и проверка взаимодействий в браузере не выполнены. Подключение к настоящему API не тестировалось, потому что его в этом макете нет.
